* Life without version control

** Five pains

#+ATTR_LATEX: :booktabs t :align p{5.2cm}p{7.6cm} :font \small
| *Pain*                      | *Consequence*                                           |
|-----------------------------+---------------------------------------------------------|
| Lost work                   | A disk crash, a bad copy-paste: days of work are gone   |
| Overwriting each other      | Last one to save wins; the other's work silently vanishes |
| No "why"                    | The code says /what/, never /why/ it became like this   |
| No way back                 | A bad change in production; nobody knows the last good state |
| No parallel work            | "Don't touch the project, I'm working on it"            |

#+BEAMER: \vfill
#+begin_center
Each pain becomes a *requirement* for a tool.
#+end_center

** Generation 3: distributed, the birth of Git (2005)

- 2002-2005: the Linux kernel uses *BitKeeper*, a proprietary distributed VCS, under a free licence
- April 2005: the licence is withdrawn after a dispute
- Linus Torvalds writes his own tool: Git manages its own source code within days; Linux 2.6.12 is released with it in June

#+BEAMER: \pause

*Design goals:*
- *Speed*: almost every operation is local
- *Fully distributed*: no mandatory central server
- *Non-linear development*: thousands of parallel branches
- *Integrity*: corruption or tampering must be detected
- Scale to a huge project (the kernel: thousands of contributors)

- You changed 5 files: a bug fix, a new feature, and a debug =print=
- The staging area lets you *choose* what goes into the next commit

#+begin_keyblock
Why it matters: a commit that does one thing can be reviewed, understood, and *undone* on its own.
#+end_keyblock

** The daily loop

#+BEAMER: \small
#+begin_example
$ git status              # what changed? what is staged?
$ git diff                # my changes, line by line
$ git add cart.py         # choose what goes into the next commit
$ git diff --staged       # review what I am about to commit
$ git commit -m "Fix crash when the cart is empty"
$ git log --oneline       # check the result
a158e2f Fix crash when the cart is empty
c337f7a Add checkout page
#+end_example
#+BEAMER: \normalsize

- =git status= is your compass: run it before and after every command, and *read* it (it often tells you the next command)
- Commit when one logical change is done: several times a day, not once a week

#+begin_keyblock
=git diff --staged= before each commit is your own first code review.
#+end_keyblock

** Reading the history

#+BEAMER: \small
#+begin_example
$ git log --oneline --graph --all     # the whole picture
$ git show a158e2f                    # one commit: author, message, diff
$ git log -p -- cart.py               # every change ever made to one file
$ git diff main feature               # what differs between two branches
$ git blame cart.py                   # who last changed each line
#+end_example
#+BEAMER: \normalsize

- Each commit has a unique *ID* (=a158e2f=), identical on every clone
- It names an *exact version* of the whole project: "=a158e2f= passed the tests", "=a158e2f= runs in production". This is how CI and CD will talk (remember Knight Capital)

#+begin_keyblock
History is only useful if you can *read* it: small commits and good messages make these commands answer real questions.
#+end_keyblock

** Undoing things

#+ATTR_LATEX: :booktabs t :align lll :font \footnotesize
| *Situation*                          | *Command*                | *After a push?*        |
|--------------------------------------+--------------------------+------------------------|
| I broke a file, I want it back       | =git restore f=          | n/a (edits are lost!)  |
| I staged a file by mistake           | =git restore --staged f= | n/a                    |
| Fix the last commit (message, file)  | =git commit --amend=     | *no*: rewrites it      |
| Undo my last local commit            | =git reset HEAD~1=       | *no*: rewrites history |
| A shared commit broke production     | =git revert <id>=        | *yes*: adds a commit   |

#+BEAMER: \vfill
#+begin_warnblock
Rule: before =push=, you may rewrite /your/ history; after =push=, only *add* to it (=revert=). Safety net: =git reflog=.
#+end_warnblock

#+begin_keyblock
Daily rhythm: =pull= \rightarrow branch \rightarrow small commits \rightarrow =pull= \rightarrow =push=. Never =push --force= on a shared branch.
#+end_keyblock

* Branches and merges

** Why branches?

#+begin_center
\large You are half-way through a new feature. \\
An urgent bug is reported in production. What do you do?
#+end_center

#+BEAMER: \pause

- Commit the half-done feature? \rightarrow you ship broken code
- Copy the project folder? \rightarrow two diverging copies, merged by hand
- Throw your work away? \rightarrow no

#+BEAMER: \pause
#+begin_keyblock
A *branch* is an isolated line of work: a feature, a fix, an experiment. It does not disturb =main= or your colleagues.
#+end_keyblock

Git compares the two tips *and their common ancestor*, which tells /who/ changed what:

#+ATTR_LATEX: :booktabs t :align llll :font \footnotesize
| *Base* | *main* | *feature* | *Result*                     |
|--------+--------+-----------+------------------------------|
| A      | A      | B         | B (only feature changed it)  |
| A      | B      | A         | B (only main changed it)     |
| A      | B      | C         | *conflict*: both changed it  |

** Conflicts are a feature, not a bug

#+BEAMER: \small
#+begin_example
<<<<<<< HEAD
TAX_RATE = 0.19
=======
TAX_RATE = 0.09
>>>>>>> feature
#+end_example
#+BEAMER: \normalsize

- Two people changed the *same lines* in different ways since the merge base
- Git *refuses to guess*: which value is right is a business decision, not a text operation

#+begin_warnblock
A tool that "always takes the most recent version" would silently ship a wrong tax rate. A conflict is a *conversation* between two developers, and the longer you wait to merge, the bigger it gets.
#+end_warnblock

** Back to the broken production

#+ATTR_LATEX: :booktabs t :align p{5.6cm}p{6.8cm} :font \small
| *Question*                            | *Git answer*                                              |
|---------------------------------------+-----------------------------------------------------------|
| What changed since last week?         | =git log --since="1 week ago"=, =git diff=                |
| Who changed this line, and why?       | =git blame=, then read the commit message                 |
| Which commit broke it?                | =git bisect=: binary search in the history                |
| Can we go back, now, safely?          | =git revert= (a new commit that undoes one change)        |

#+BEAMER: \vfill
#+begin_keyblock
Each answer works only if commits are *small*, have a *good message*, and *everything* is versioned.
#+end_keyblock

** Key takeaways

1. Version control = *time machine* + *collaboration protocol*; everything that builds and runs the system is versioned
2. Each generation of VCS fixed the problems of the previous one; Git: *distributed*, *fast*, *trustworthy*
3. Daily loop: =status=, =add=, =commit=, =pull=, =push=; the staging area makes each commit *one logical change*
4. Undo safely: rewrite only what is not pushed; once shared, =revert=. A commit ID names an *exact version*
5. Branches are *cheap pointers*; conflicts are Git *refusing to guess*
6. Integrate *small and often*: long-lived branches recreate the vicious circle
