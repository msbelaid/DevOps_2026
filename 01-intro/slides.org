** A story: Knight Capital, August 1st, 2012
:PROPERTIES:
:BEAMER_opt: t
:END:

- Knight Capital: one of the largest US stock traders (~17% of NYSE volume)
- Night before: new trading code deployed *by hand* to 8 servers
- One server was *not updated*: still running old, dead code
- A reused configuration flag reactivated that dead code
- 9:30 market opens: the 8th server sends millions of unwanted orders
- 97 automated warning e-mails before opening: nobody acted on them
- *45 minutes* to stop it \rightarrow *\dollar{}440 million lost*
- The company was sold a few months later

#+BEAMER: \vfill
#+begin_center
\footnotesize Source: U.S. SEC, Administrative Proceeding File No. 3-15570 (2013)
#+end_center

** What went wrong?

#+begin_center
\Large Was this a /developer/ bug? An /operations/ mistake? Both? Neither?
#+end_center

#+BEAMER: \pause

- Manual, unrepeatable deployment
- No automated check that all servers were identical
- Dead code kept in production, flags reused
- Alerts that nobody watched or understood
- No quick, rehearsed way to roll back

#+BEAMER: \pause
#+begin_warnblock
None of these is a "coding" problem. They are problems of *process, automation, feedback and collaboration*, which is exactly what DevOps is about.
#+end_warnblock

** "Done" is not "delivered"

#+begin_center
\Large "It's done, it just isn't deployed yet."
#+end_center

#+BEAMER: \vspace{0.5cm}

- A feature has *zero value* until users can use it
- Code waiting to be deployed = *inventory* (Lean): it costs money, hides bugs, and gets stale
- Agile optimised a part of the chain; the bottleneck moved to *delivery and operations*

#+BEAMER: \vfill
#+begin_keyblock
Lean idea: optimise the *whole value stream*, from idea to user, not each team separately.
#+end_keyblock

* The Dev vs Ops problem

** Two teams, two missions

*** Dev
:PROPERTIES:
:BEAMER_col: 0.48
:BEAMER_env: block
:END:

- Mission: *deliver change* (new features, fixes)
- Rewarded for: speed, features shipped
- Environment: laptop, test server
- Sees production as: "someone else's problem"

*** Ops
:PROPERTIES:
:BEAMER_col: 0.48
:BEAMER_env: alertblock
:END:

- Mission: *keep things stable* (availability, security)
- Rewarded for: uptime, no incidents
- Environment: real servers, real load, real data
- Sees change as: "the main cause of outages"

*** Conclusion
:PROPERTIES:
:BEAMER_env: ignoreheading
:END:

#+BEAMER: \vspace{0.4cm}
#+begin_center
Both are rational. Their goals are *structurally opposed*: \\
every change Dev wants is a risk Ops must absorb.
#+end_center

** Symptom 1: "It works on my machine"

- Dev environment \ne test environment \ne production environment
  - different OS versions, libraries, configuration, data, network
- Installation instructions in a Word document or a wiki page (outdated)
- Bugs that appear /only/ in production, and nobody can reproduce them

#+BEAMER: \vfill
#+begin_keyblock
Root cause: the *environment* is not part of what is versioned, tested and delivered.
#+end_keyblock

\footnotesize \rightarrow Answers: containers and Infrastructure as Code

#+end_warnblock

** Symptom 3: snowflake servers

- Servers configured *by hand*, over years, by different people
- Each server is unique, fragile, impossible to rebuild identically
- "Don't reboot that one, nobody knows how it works"
- *Configuration drift*: two "identical" servers slowly become different (remember Knight Capital!)

#+BEAMER: \vfill
#+begin_center
\large "Pets vs cattle": we name and nurse pets; cattle are numbered and replaceable.
#+end_center

\footnotesize \rightarrow Answers: orchestration and Infrastructure as Code

** Symptom 4: silos and blame

- Each team optimises its own metric, not the global outcome
- Communication through tickets and hand-offs: waiting time everywhere
- Incident \rightarrow "who did it?" \rightarrow people hide mistakes
- Hidden mistakes \rightarrow no learning \rightarrow the same incident again

#+BEAMER: \vfill
#+begin_warnblock
A culture of fear makes systems *less* safe: problems are reported late, or never.
#+end_warnblock

* What DevOps is (and is not)

** Defining DevOps

#+begin_quote
"DevOps is a set of practices intended to reduce the time between committing a change to a system and the change being placed into normal production, while ensuring high quality." \\
\hfill Bass, Weber, Zhu, /DevOps: A Software Architect's Perspective/, 2015
#+end_quote

#+BEAMER: \vspace{0.3cm}

*Working definition for this course:*

#+begin_keyblock
DevOps is a *culture* and a set of *practices* that bring development and operations together, so that software can be delivered *quickly, safely and repeatedly*, with fast *feedback* from production.
#+end_keyblock

** What DevOps is NOT

- *Not a tool*: installing Jenkins or Kubernetes does not make you "DevOps"
- *Not a job title*: a "DevOps engineer" alone cannot fix a siloed organisation
- *Not a new silo*: a "DevOps team" between Dev and Ops = a third wall
- *Not only automation*: automating a bad process gives a fast bad process
- *Not "NoOps"*: operations do not disappear, they become shared and automated
- *Not only for start-ups*: banks, governments, industry do it too

** CALMS: the five pillars

#+ATTR_LATEX: :booktabs t :align lll :font \small
| *Pillar*     | *Idea*                                  | *Example*                          |
|--------------+-----------------------------------------+------------------------------------|
| Culture      | Shared responsibility, trust, no blame  | Dev is on call for its service     |
| Automation   | Remove manual, repetitive, risky work   | CI/CD pipeline, IaC                |
| Lean         | Small batches, limit work, flow         | Small pull requests, daily deploys |
| Measurement  | Decisions based on data                 | DORA metrics, monitoring           |
| Sharing      | Knowledge, tools and goals are shared   | Shared dashboards, postmortems     |

** Blameless postmortems

#+begin_center
\large "The question is not /who/ caused the failure, but /how/ our system allowed it."
#+end_center

#+BEAMER: \vspace{0.3cm}

- After each incident, write a postmortem: timeline, impact, causes, actions
- Assume people acted reasonably with the information they had
- Fix the *system* (process, tooling, alerts), not the person
- Share it widely: everybody learns

#+begin_keyblock
Knight Capital again: "the technician forgot a server" is a *symptom*. The cause is a deployment process that /allowed/ forgetting a server.
#+end_keyblock

* Measuring DevOps

** Why measure?

- "Without data, you're just another person with an opinion" (W. E. Deming, attributed)
- Measure *outcomes* (value for users), not *outputs* (lines of code, number of commits)
- Measure *teams and systems*, never individuals

#+BEAMER: \vfill
#+begin_warnblock
Goodhart's law: "When a measure becomes a target, it ceases to be a good measure."
#+end_warnblock

** Key takeaways

1. Dev and Ops had *opposed goals*: change vs stability \rightarrow a wall of confusion
2. Big, rare, manual releases are *more* risky, not less
3. DevOps is a *culture* + *practices* + *tools*, in that order
4. CALMS and the Three Ways: flow, feedback, learning
5. Speed and stability *go together* (DORA)
6. Every tool in this course answers a *problem*: always ask "why?"
