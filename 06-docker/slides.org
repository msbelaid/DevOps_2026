- A VM boots a *whole OS*: GBs, minutes to start, strong isolation

** Lighter, so what?

#+ATTR_LATEX: :booktabs t :align p{4.4cm}p{8cm} :font \small
| *Property*                 | *What it makes possible*                                  |
|----------------------------+-----------------------------------------------------------|
| Starts in a second         | A fresh, clean container for every CI run, every test     |
| A few MBs per app          | Dozens of apps on one server, each with its own libraries |
| Built from a text file     | Rebuilt in minutes, by anyone, on any machine             |
| Same kernel as the host    | A Linux image needs Linux: Docker Desktop hides a small VM on macOS and Windows |

#+BEAMER: \vfill
#+begin_keyblock
A VM per app was too expensive, so teams shared servers, and their conflicts. A container per app is cheap: isolation becomes the default.
#+end_keyblock

** A container is a process

=docker run= starts a normal Linux *process*, with walls around it. Each wall answers a problem:

#+ATTR_LATEX: :booktabs t :align p{4.6cm}p{7.8cm} :font \small
| *Wall*                          | *Why we want it*                                        |
|---------------------------------+---------------------------------------------------------|
| Its own *files* (the image)     | Two apps, two versions of a library, no conflict        |
| Its own *network* and ports     | Two apps can both listen on port 8000                   |
| Its own *process list*          | An app cannot see, or kill, its neighbours              |
| *Limits* on CPU and memory      | One memory leak cannot take the whole server down       |

#+BEAMER: \vfill

- The walls are Linux features (namespaces, cgroups), not a new computer
- Stop the process, and the container stops

#+BEAMER: \vfill
#+begin_keyblock
Not a small VM: an isolated process. That is why it starts so fast.
#+end_keyblock

* Building an image

** A Dockerfile

*** Left
:PROPERTIES:
:BEAMER_col: 0.55
:END:

#+BEAMER: \scriptsize
#+begin_example
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir \
      -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["flask", "--app", "app", "run",
     "--host", "0.0.0.0", "--port", "8000"]
#+end_example
#+BEAMER: \normalsize

*** Right
:PROPERTIES:
:BEAMER_col: 0.45
:END:

- A text file named =Dockerfile=, in the repository, *next to the code*
- Reviewed in a pull request like any code
- The install document, but *executable*: it cannot be out of date

** Reading the Dockerfile

#+ATTR_LATEX: :booktabs t :align p{4.3cm}p{8.4cm} :font \footnotesize
| *Line*                    | *What it does, and why*                                         |
|---------------------------+-----------------------------------------------------------------|
| =FROM python:3.12-slim=   | Official image with Python: no install by hand, version pinned  |
| =WORKDIR /app=            | Work in =/app=: one known place for the next lines and =CMD=    |
| =COPY requirements.txt .= | Copy the dependency list *alone*, for the cache (next slides)   |
| =RUN pip install ...=     | Run at *build* time: installed once, not at every start         |
| =COPY . .=                | Copy the code *last*, because it changes most often             |
| =EXPOSE 8000=             | Document the port, for readers and tools; it publishes nothing  |
| =CMD [...]=               | Run when a *container starts*: every container starts the same way |

#+BEAMER: \vfill
#+begin_keyblock
=RUN= happens once, when the image is built. =CMD= happens every time a container starts.
#+end_keyblock

** Tags and versions

#+ATTR_LATEX: :booktabs t :align p{4.2cm}p{8.2cm} :font \small
| *Tag*                 | *What it says*                                            |
|-----------------------+-----------------------------------------------------------|
| =shop:1.1.0=          | A release, semantic versioning (lecture 5)                |

| =shop:latest=         | Only "the last one built here". Default when no tag given |

- The tag answers "what exactly runs in production?"
- One image can have several tags: =1.1.0= and =4b23633= for the same build

#+end_warnblock

** Good habits

#+ATTR_LATEX: :booktabs t :align p{5cm}p{7.4cm} :font \small
| *Habit*                                 | *Why*                                              |
|-----------------------------------------+----------------------------------------------------|
| A small base image (=-slim=)            | Faster to download, less software to attack        |
| Pin versions (Python 3.12, Flask 3.1.2) | Same build today and in six months |
| Dependencies before code                | Fast builds thanks to the cache                    |
| No secrets in the image                 | Images are copied and shared                       |
| Only runtime packages, no pytest        | Smaller, fewer tools for an attacker               |
| A =USER= that is not =root=             | A hacked app gets fewer rights                     |
| One process per container               | Easy to start, stop, scale and read the logs       |

- =-p HOST:CONTAINER= publishes a port of the container on the laptop
- Without =-p=, the app runs but nobody outside can reach it
- Inside, the app must listen on =0.0.0.0=: =127.0.0.1= is the container's *own* localhost

#+BEAMER: \vfill
#+begin_keyblock
Why this indirection? Two shops can run side by side, both on 8000 inside: =-p 8001:8000= and =-p 8002:8000=. The app never changes, only the mapping.
#+end_keyblock

** Containers are disposable

- A container writes in its own *writable layer*
- =docker rm=: the layer is gone, and every file written in it
- A new container always starts from the *same* image, in the same state

#+BEAMER: \vfill

#+begin_keyblock
Good: no "fixed by hand inside the container". The fix goes into the Dockerfile, then a new image.
#+end_keyblock

#+begin_warnblock
Bad for data: a database in a container needs a *volume* outside it (next session).
#+end_warnblock

** What Docker does not solve

#+ATTR_LATEX: :booktabs t :align p{3.8cm}p{8.6cm} :font \footnotesize
| *Limit*                 | *Why, and what helps*                                          |
|-------------------------+----------------------------------------------------------------|
| Weaker isolation        | One shared kernel: a kernel flaw reaches every container       |
| Data is lost on =rm=    | Volumes, managed databases (session 7)                         |
| Many servers            | Who restarts and balances containers? Kubernetes (session 8)   |
| Bugs in your code       | Same image everywhere, *same bug* everywhere: tests still matter |
| Old packages            | An image ages: rebuild it often, scan it for known flaws       |

#+BEAMER: \vfill
#+begin_keyblock
Docker removes the differences *between* machines. It does not make the software correct or the server safe.
#+end_keyblock

** Key takeaways

1. Code in Git is not enough: the *environment* must travel with it, or each machine breaks it differently
2. A container is an *isolated process* sharing the host's kernel: light, so we can afford one per app and a fresh one per test
3. The *image* is read-only, so what CI tested is what production runs
4. Order the Dockerfile for the *cache*; keep secrets out, because images are copied
5. Containers are *disposable* (cattle, not pets): configuration from outside, data in volumes
6. The *image* is the artifact: built once by CI, tagged with the commit, so we always know what runs
