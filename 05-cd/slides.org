** What is continuous delivery?

#+begin_center
\large "Continuous Delivery is the ability to get changes of all types (new features, configuration changes, bug fixes and experiments) into production, or into the hands of users, *safely and quickly* in a *sustainable* way."

\hfill J. Humble, continuousdelivery.com
#+end_center

#+BEAMER: \vfill

- *All types*: not only features. A config change or an urgent fix takes the same road
- *Safely and quickly*, together: not one against the other
- *Sustainable*: no release nights, no heroes

#+begin_keyblock
Goal: =main= is *always* releasable. Releasing becomes a business decision, not a technical event.
#+end_keyblock

** If it hurts, do it more often

- Integration, testing, deployment: painful tasks get *worse* when postponed
  - more changes pile up, steps are forgotten, nobody remembers how
- Doing them often *forces* you to make them small and to automate them
- Lecture 2: integrate often. Lecture 4: test every change. Today: deploy every change

#+BEAMER: \vfill
#+begin_keyblock
"If it hurts, do it more often, and bring the pain forward." (J. Humble, D. Farley, /Continuous Delivery/)
#+end_keyblock

** Measuring delivery: the four DORA metrics

#+ATTR_LATEX: :booktabs t :align p{3.4cm}p{5.4cm}p{3.6cm} :font \small
| *Metric*                | *Question*                                     | *Elite teams*       |
|-------------------------+------------------------------------------------+---------------------|
| Deployment frequency    | How often do we deploy to production?          | On demand, daily    |
| Lead time for changes   | From commit to production, how long?           | Less than one day   |
| Change failure rate     | Which share of deployments causes a failure?   | Low                 |
| Time to restore service | After a failure, how long to recover?          | Less than one hour  |

#+BEAMER: \vfill

- Two metrics for *speed*, two for *stability*
- N. Forsgren, J. Humble, G. Kim, /Accelerate/ (2018), and the yearly DORA reports

- Deploy several times a day

** Build once, deploy everywhere

*** Wrong
:PROPERTIES:
:BEAMER_col: 0.5

:END:

- Build for staging, test it
- *Build again* for production
- Production runs a binary that nobody tested (other dependency version, other machine)

*** Right
:PROPERTIES:
:BEAMER_col: 0.5

:END:

- Build *once*, in the pipeline
- Deploy the *same* artifact to staging, then to production
- Only the *configuration* changes between them

:PROPERTIES:
:BEAMER_env: ignoreheading
:END:

#+begin_keyblock
What was tested in staging is *byte for byte* what reaches production.
#+end_keyblock

** A deployment in GitHub Actions

*** Left
:PROPERTIES:
:BEAMER_col: 0.55
:END:

#+BEAMER: \tiny
#+begin_example
  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python build.py
      - uses: actions/upload-pages-artifact@v3
        with:
          path: site

  deploy:
    needs: build
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    permissions:
      pages: write
      id-token: write
    environment: github-pages
    steps:
      - uses: actions/deploy-pages@v4
#+end_example
#+BEAMER: \normalsize

*** Right
:PROPERTIES:
:BEAMER_col: 0.45
:END:

- Two more jobs in =ci.yml=, after =test=
- =needs=: a chain, each job waits for the previous one to be *green*
- =build= runs for every PR too: a build error is caught *before* the merge
- =deploy= runs only after a merge into =main=
- =deploy= does not build: it publishes the artifact of =build=

** Reading the deployment jobs

#+ATTR_LATEX: :booktabs t :align p{5.4cm}p{7.3cm} :font \footnotesize
| *Line*                               | *Meaning*                                                  |
|--------------------------------------+------------------------------------------------------------|
| =needs: test=                        | Start only if =test= is green                              |
| =upload-pages-artifact=              | Store the built folder as the artifact of this run         |
| =if: github.event_name == 'push'=    | Deploy after a merge, never for a pull request             |
| =permissions: pages: write=          | This job, and only this one, may publish                   |
| =id-token: write=                    | Prove who asks, without a stored password |
| =environment: github-pages=          | The target; its protection rules apply                     |
| =deploy-pages=                       | Publish the artifact built earlier, in the same run        |

#+BEAMER: \vfill
#+begin_keyblock
Least privilege: the test and build jobs cannot publish anything; only =deploy= can.
#+end_keyblock

** Environments in GitHub

- Settings > Environments: one per target (=staging=, =production=, =github-pages=)
- *Protection rules*:
  - Required reviewers: the job waits until a person *approves*
  - Deployment branches: only =main= may deploy
  - Wait timer: wait N minutes before deploying
- *Secrets per environment*: the production password is not the staging one
- *History*: the list of deployments, with what, when and who

#+BEAMER: \vfill
#+begin_keyblock
One setting, "Required reviewers", turns continuous deployment into continuous delivery.
#+end_keyblock

* Releasing safely

** Deploying is not releasing

*** Left
:PROPERTIES:
:BEAMER_col: 0.5
:END:

- *Deploy*: the new code is on the servers
- *Release*: users can see the feature
- A *feature flag* separates the two

#+BEAMER: \scriptsize
#+begin_example
if flags.enabled("new_checkout", user):
    show_new_checkout()
else:
    show_old_checkout()
#+end_example
#+BEAMER: \normalsize

*** Right
:PROPERTIES:
:BEAMER_col: 0.5
:END:

- Merge unfinished work, hidden behind a flag: short branches (lecture 2)
- Turn it on for the team, then 10% of users, then everyone
- A problem? Turn it off in one second, no deployment

*** Conclusion
:PROPERTIES:
:BEAMER_env: ignoreheading
:END:

#+BEAMER: \vfill
#+begin_warnblock
Flags are debt: remove each flag once the feature is fully released.
#+end_warnblock

** Deployment strategies

#+ATTR_LATEX: :booktabs t :align p{2.3cm}p{5.2cm}p{1.8cm}p{3.2cm} :font \small
| *Strategy* | *How*                                        | *Downtime* | *Rollback*              |
|------------+----------------------------------------------+------------+-------------------------|
| Recreate   | Stop the old version, start the new one      | Yes        | Redeploy the old one    |
| Rolling    | Replace the servers one by one               | No         | Slow, server by server  |
| Blue-green | Two identical productions, switch the traffic | No        | Switch back: seconds    |
| Canary     | New version for a small share of users first | No         | Stop the canary         |

#+BEAMER: \vfill
#+begin_keyblock
Choose by risk and cost: blue-green doubles the servers; canary needs good monitoring to see a problem.
#+end_keyblock

- The name: miners took a canary into the mine; if the bird fell ill, they got out

** When it goes wrong

*** Do
:PROPERTIES:
:BEAMER_col: 0.5
:BEAMER_env: block
:END:

- *Roll back*: =git revert= (lecture 2), the pipeline redeploys the old behaviour
- Or redeploy the *previous artifact*
- *Roll forward* (fix and deploy) only if the fix is obvious and the pipeline fast
- Then add the missing test

*** Don't
:PROPERTIES:
:BEAMER_col: 0.5
:BEAMER_env: alertblock
:END:

- Fix it by hand on the server, with ssh
  - the next deployment erases the fix
  - nobody knows what runs in production
- Wait for "the person who knows"

*** Conclusion
:PROPERTIES:
:BEAMER_env: ignoreheading
:END:

#+BEAMER: \vfill
#+begin_keyblock
Time to restore is a metric. A rollback that is *routine* is the best insurance.
#+end_keyblock

** Key takeaways

1. A green =main= that is not deployed delivers *nothing*
2. Small, frequent releases are *faster and safer* (DORA: speed and stability together)
3. *Delivery*: always deployable, a person decides. *Deployment*: every green change goes out
4. One pipeline, the only road to production; *build once*, deploy the same artifact
5. Deploying is not releasing: feature flags, blue-green, canary
6. Plan the failure: rollback must be fast and routine; versions tell what changed
