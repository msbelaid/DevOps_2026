* Why other eyes? Code review

** Why review code?

*** What a reviewer catches
:PROPERTIES:
:BEAMER_col: 0.5
:BEAMER_env: block
:END:

- Bugs and missing cases ("what if the cart is empty?")
- Unclear names, duplicated code
- Design problems, security holes
- Missing tests

*** What the team gains
:PROPERTIES:
:BEAMER_col: 0.5
:BEAMER_env: block
:END:

- *Two* people know each part of the code
- Juniors learn from seniors, and the reverse
- Shared style and conventions
- A record of *why*, in the discussion

*** Conclusion
:PROPERTIES:
:BEAMER_env: ignoreheading
:END:

#+BEAMER: \vfill
#+begin_keyblock
Review is not a *judgement* of the author: it is the team taking *shared ownership* of the code (lecture 1: blameless culture).
#+end_keyblock

** What the evidence says

#+ATTR_LATEX: :booktabs t :align p{6cm}r :font \small
| *Technique* (McConnell, /Code Complete/, 2004) | *Defects found (typical)* |
|------------------------------------------------+---------------------------|
| Informal code review                           | 25%                       |
| Unit tests                                     | 30%                       |
| Integration tests                              | 35%                       |
| Formal code inspection                         | 60%                       |

- No single technique finds most defects: *combine* them
- Microsoft (Bacchelli & Bird, 2013) and Google (Sadowski et al., 2018): review finds bugs, but brings even more *knowledge transfer* and better code

#+begin_keyblock
Review and tests are *complementary*: today we do both.
#+end_keyblock

** The bus factor

#+begin_center
\large How many people must be hit by a bus \\
before the project stops?
#+end_center

#+BEAMER: \pause

- Bus factor = 1: only one person understands the payment code
- They are sick, on holiday, or leave the company \rightarrow nobody can fix a bug in production
- Every review spreads knowledge: the reviewer now *knows* this code

#+BEAMER: \vfill
#+begin_keyblock
Code review is the cheapest way to raise the bus factor: knowledge spreads *as a side effect* of daily work.
#+end_keyblock

- A *pull request* (PR): "please pull my branch into =main=", plus a place to *discuss* it
- Commits pushed to the branch *update* the PR automatically

#+begin_keyblock
A pull request turns a branch into a *team decision*: nobody merges alone.
#+end_keyblock

** GitHub flow (S. Chacon, 2011)

1. =main= is *always deployable*
2. Create a *descriptively named* branch from =main= (=fix/discount-limit=)
3. Commit locally, *push* the branch often
4. Open a pull request when you want feedback, or when you are done
5. Merge *after* review and green checks
6. Deploy right after the merge; delete the branch

#+BEAMER: \vfill
#+begin_keyblock
Short-lived branches + a PR as the gate to =main=: the *trunk-based* idea of lecture 2, made safe.
#+end_keyblock

** Three merge buttons

#+ATTR_LATEX: :booktabs t :align p{3cm}p{5.5cm}p{4.3cm} :font \footnotesize
| *Button*          | *Result on =main=*                                  | *Good for*                         |
|-------------------+-----------------------------------------------------+------------------------------------|
| Merge commit      | All commits of the branch + a merge commit          | Keeping the full real history      |
| Squash and merge  | *One* commit with all the changes of the PR         | Clean history: one PR = one commit |
| Rebase and merge  | The commits replayed on top of =main=, no merge commit | Linear history, commits kept    |

#+BEAMER: \vfill

- Same choice as lecture 2 (merge or rebase?), now made *on GitHub*
- Squash: the "wip" and "fix typo" commits of the branch disappear from =main=

#+begin_keyblock
Pick one convention per project and write it down. In our labs: *squash and merge*.
#+end_keyblock

** Protecting =main=

*** Left
:PROPERTIES:
:BEAMER_col: 0.52
:END:

A *branch rule* (GitHub ruleset) on =main=:
- *Require a pull request*: no direct push
- *Require 1 approval*: the author cannot approve their own PR
- *Block force pushes* and deletion
- *Require status checks*: tests must pass (next session)

*** Right
:PROPERTIES:
:BEAMER_col: 0.48
:END:

* Code review in practice

** What to look for, what to leave to machines

*** Humans
:PROPERTIES:
:BEAMER_col: 0.5
:BEAMER_env: block
:END:

- Does it do what the issue asks?
- Missing cases: empty, zero, negative, too big
- Are there *tests* for the new behaviour?
- Can I understand it without the author?
- Is it the right design?

*** Machines
:PROPERTIES:
:BEAMER_col: 0.5
:BEAMER_env: alertblock
:END:

- Formatting, spaces, line length (formatter)
- Unused variables, style rules (linter)
- "Do the tests still pass?" (CI)
- Known vulnerable libraries (scanner)

*** Conclusion
:PROPERTIES:
:BEAMER_env: ignoreheading
:END:

#+BEAMER: \vfill
#+begin_keyblock
Do not spend human attention on what a tool can check: reviewers should argue about *behaviour and design*, not commas.
#+end_keyblock

** Writing review comments

*** Bad
:PROPERTIES:
:BEAMER_col: 0.45
:BEAMER_env: alertblock
:END:

#+BEAMER: \small
- "This is wrong."
- "Why would anyone write this?"
- "Use a list comprehension." (on a style choice)
- 40 comments on spaces
#+BEAMER: \normalsize

*** Good
:PROPERTIES:
:BEAMER_col: 0.55
:BEAMER_env: block
:END:

#+BEAMER: \small
- "What happens with ~percent = 150~? Could we add a test?"
- "I find =shipping_cost= clearer than =sc=, what do you think?"
- "nit: typo in the docstring" (minor, optional)
- "Nice idea, I did not know this function!"
#+BEAMER: \normalsize

*** Conclusion
:PROPERTIES:
:BEAMER_env: ignoreheading
:END:

#+BEAMER: \vfill
- Comment the *code*, never the *person*; ask questions; explain *why*
- Say clearly what *blocks* the merge and what is only a suggestion

** Being reviewed

- Read your own diff on GitHub *before* asking for review: you will find half of the problems
- Keep the PR *small*, with a description that explains *why* and *how to test*
- Answer *every* comment: fix it, or explain why not
- A comment on your code is not an attack on you: *you are not your code*
- Disagreement? Talk (or call) instead of a 30-message thread

#+BEAMER: \vfill
#+begin_keyblock
Good review is a *conversation* between two people who want the same thing: working code in =main=.
#+end_keyblock

* Writing tests with pytest

** A first test

*** Left
:PROPERTIES:
:BEAMER_col: 0.55

#+begin_example
# test_cart.py
from cart import average

def test_average():
    # arrange
    prices = [10, 20]
    # act
    result = average(prices)
    # assert
    assert result == 15
#+end_example

*** Right

:BEAMER_col: 0.45
:END:

- A test is a *function* whose name starts with =test_=, in a file =test_*.py=
- *Arrange*, *act*, *assert*
- =pytest= finds and runs them all

#+begin_example
$ pytest

#+end_example

** Reading a failure

$ pytest

- *Which* test failed, on *which line*, with *which values*: =average([])= returned =None=, not =0=
- A red test is *good news*: the bug was found on your laptop, not by a customer

** What to test?

#+ATTR_LATEX: :booktabs t :align p{3.4cm}p{9.2cm} :font \small
| *Kind of case*      | *Example for the shop*                                         |
|---------------------+----------------------------------------------------------------|
| Normal case         | ~average([10, 20]) == 15~                                      |
| Empty / zero        | ~average([]) == 0~, ~total([]) == 0~                           |
| Boundaries          | Free shipping "from 50": test 49, *50*, 51                     |
| Invalid input       | =apply_discount([100], 150)= must *raise* an error             |

#+BEAMER: \small
#+begin_example
import pytest

def test_discount_over_100_is_refused():
    with pytest.raises(ValueError):
        apply_discount([100], 150)
#+end_example
#+BEAMER: \normalsize

#+begin_keyblock
Bugs live at the *edges*: empty, zero, boundaries, invalid input. Test those first.
#+end_keyblock

** A bug? Write the test first

#+begin_export latex

  arr/.style={-Stealth, very thick}]
  \node[s, fill=opscol!20] (r) at (0,0) {\textbf{1. Red}\\ \scriptsize a test reproduces the bug};

- The issue says "150% gives negative prices": first, a *test* that fails for this reason
- Then fix: the test turns green. You *know* the fix works
- The test stays forever: this bug can never come back silently (*regression test*)
- Writing tests before the code for *everything*: Test-Driven Development (K. Beck, 2002)

#+begin_keyblock
Never fix a bug without a test that proves it: otherwise it *will* come back.
#+end_keyblock

** Coverage: a measure, not a goal

*** Left
:PROPERTIES:
:BEAMER_col: 0.5
:END:

- *Coverage*: % of lines run by the tests (=pytest --cov=, plugin =pytest-cov=)
- Low coverage: whole parts are *never* tested. Useful alarm
- High coverage does not mean good tests

*** Right
:PROPERTIES:
:BEAMER_col: 0.5
:END:

#+BEAMER: \small
#+begin_example
def test_discount():
    apply_discount([100], 10)
    # 100% coverage of
    # apply_discount...
    # and no assert!
#+end_example
#+BEAMER: \normalsize

*** Conclusion
:PROPERTIES:
:BEAMER_env: ignoreheading
:END:

#+BEAMER: \vfill
#+begin_warnblock
Goodhart's law: "when a measure becomes a target, it ceases to be a good measure". Aim for tests that *would fail* if the code broke, not for a number.
#+end_warnblock

** Good unit tests: FIRST

#+ATTR_LATEX: :booktabs t :align p{3cm}p{9.6cm} :font \small
| *Property*         | *Why*                                                            |
|--------------------+------------------------------------------------------------------|
| \textbf{F}ast        | Milliseconds: you run them after every change, without thinking |
| \textbf{I}ndependent | Any order, alone or together: one test never depends on another |
| \textbf{R}epeatable  | Same result on every laptop, every day (no network, no clock)   |
| \textbf{S}elf-validating | Pass or fail, no human reading the output                   |
| \textbf{T}imely      | Written with the code (or before), not "later"                  |

#+BEAMER: \vfill
#+begin_keyblock
A slow or random ("flaky") test is soon ignored by everyone: it is worse than no test.
#+end_keyblock

** Key takeaways

1. Review catches bugs, but above all *spreads knowledge* (bus factor) and builds *shared ownership*
2. GitHub flow: short branch \rightarrow pull request \rightarrow review \rightarrow merge; =main= is always deployable
3. Small PRs, linked to an issue, reviewed with kind and precise comments
4. Protect =main=: the safe path must be the *only* path
5. Automated tests replace "I tried it once"; they give the *courage to change*
6. Test the edges; for each bug, write the failing test *first*
