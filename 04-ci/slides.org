** What is continuous integration?

#+begin_center
\large "Continuous Integration is a software development practice where members of a team *integrate their work frequently*, usually each person integrates at least daily. Each integration is *verified by an automated build* (including tests) to detect integration errors as quickly as possible."

\hfill M. Fowler, 2006
#+end_center

#+BEAMER: \vfill

- Two halves: a *habit* (integrate daily into =main=) and a *machine* (verify each integration)
- A CI server on a project where branches live 3 weeks is *not* CI

#+begin_keyblock
CI is a *practice* first. The tool only makes the practice affordable.
#+end_keyblock

** The rules of CI

1. Everyone integrates into =main= at least *daily*
2. Every push triggers an *automated* build and tests
3. The build is *fast*: under 10 minutes, ideally under 5
4. A red =main= is the team's *top priority*: fix it or revert it, now
5. Everybody *sees* the result; nobody merges on red

#+BEAMER: \vfill
#+begin_keyblock
Rule 4 is the "stop the line" of Toyota factories: when something is broken, the whole team stops to fix it, instead of building on top of it.
#+end_keyblock

** A first workflow

*** Left
:PROPERTIES:
:BEAMER_col: 0.55
:END:

#+BEAMER: \scriptsize
#+begin_example
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements-dev.txt
      - run: pytest
#+end_example
#+BEAMER: \normalsize

*** Right
:PROPERTIES:
:BEAMER_col: 0.45
:END:

- A YAML file, *versioned with the code*: reviewed in PRs like any code
- =on=: when to run
- =jobs=: what to run, and where
- 17 lines replace "did you run the tests?"

#+begin_warnblock
YAML is indentation-sensitive: spaces, never tabs.
#+end_warnblock

** Reading the workflow

#+ATTR_LATEX: :booktabs t :align ll :font \footnotesize
| *Line*                       | *Meaning*                                                  |
|------------------------------+------------------------------------------------------------|
| =push= on =main=             | Run after each merge into =main=                           |
| =pull_request=               | Run for each PR, and each new commit pushed to it          |
| =runs-on: ubuntu-latest=     | A fresh Ubuntu virtual machine, destroyed after the job    |
| =actions/checkout@v4=        | Copy the repository (only what is committed!)              |
| =actions/setup-python@v5=    | Install the requested Python version                       |
| =pip install -r ...=         | Install exactly the declared dependencies                  |
| =pytest=                     | A failing command (exit code \(\neq\) 0) makes the job red |

#+BEAMER: \vfill
#+begin_keyblock
A red job is just a command that *failed*: =pytest= fails when a test fails.
#+end_keyblock

** Events: when should CI run?

#+ATTR_LATEX: :booktabs t :align p{3.6cm}p{9.1cm} :font \small
| *Event*                   | *Typical use*                                                    |
|---------------------------+------------------------------------------------------------------|
| =pull_request=            | Check a change *before* the merge: the main use                  |
| =push= on =main=          | Check =main= *after* the merge (and later: deploy it)            |
| =schedule= (cron)         | Every night: slow tests, dependency vulnerabilities              |
| =workflow_dispatch=       | A "Run workflow" button, for manual runs                         |

#+BEAMER: \vfill

- Why not =push= on every branch? With =pull_request= too, each commit of a PR would run *twice*
- Next sessions: the same file grows into a delivery pipeline (=push= on =main= \rightarrow deploy)

** Actions: reusable steps

- =uses: actions/checkout@v4=: code written by someone else, run *in your pipeline*
- Thousands on the GitHub Marketplace: set up a language, cache, deploy, notify...
- =@v4= *pins a version*: an update cannot change your pipeline without you knowing

#+BEAMER: \vfill
#+begin_warnblock
An action runs with access to your code and your pipeline's token. Prefer official or well-known actions, and pin their version (or even their commit ID).
#+end_warnblock

#+BEAMER: \vfill
- Lecture 1 again: the pipeline is *code*, so it gets the same care as code: review, versions, history

** Fast feedback

- A 40-minute pipeline: developers stop waiting, switch tasks, batch their changes. Back to big batches
- *Fail fast*: cheap checks first (lint: seconds), slow ones after (tests)
- *Cache* the dependencies between runs: =setup-python= with =cache: pip=
- *Parallel jobs*: lint and test at the same time, on different runners
- Slow tests (end-to-end) in a separate, less frequent workflow (=schedule=)

#+BEAMER: \vfill
#+begin_keyblock
Target: the answer arrives before you have switched to another task, *under 10 minutes*.
#+end_keyblock

** CI is only as good as its checks

*** Left
:PROPERTIES:
:BEAMER_col: 0.5
:END:

- CI runs *your* checks, nothing more: no tests \rightarrow a green pipeline that proves nothing
- Green means "*the checks we wrote* passed", not "the app works"
- Lecture 3: unit tests for =cart.py=. But a bug can hide in many other places

*** Right
:PROPERTIES:

Two questions (B. Boehm, 1979):
- *Verification*: are we building the product *right*? It matches the spec (tests, lint, types)
- *Validation*: are we building the *right* product? Users want it (acceptance, demos, feedback)

- A linter never finds a wrong tax rate; a unit test never finds a missing file

No single check catches everything. Each kind of check answers a *different question*.

** Static checks: read the code, do not run it

#+ATTR_LATEX: :booktabs t :align p{2.4cm}p{6.4cm}p{4.2cm} :font \scriptsize
| *Check*         | *Question it answers*                          | *Python tools*                |
|-----------------+------------------------------------------------+-------------------------------|
| Formatting      | Is the layout consistent?                      | =ruff format=, =black=        |
| Linting         | Unused import, undefined name, suspicious code? | =ruff=, =pylint=              |
| Type checking   | Do we pass a =str= where a =float= is expected? | =mypy=, =pyright=             |
| Security (SAST) | =eval()=, SQL built by hand, weak crypto?      | =bandit=, CodeQL              |
| Dependencies    | Do our libraries have known vulnerabilities?   | =pip-audit=, Dependabot       |
| Secrets         | Did someone commit a password or token?        | =gitleaks=, GitHub scanning   |

#+BEAMER: \vfill
#+begin_keyblock
Static checks are *cheap* (seconds) and need *no test to write*: put them first in the pipeline.
#+end_keyblock

** Functional tests: does it do the right thing?

#+ATTR_LATEX: :booktabs t :align p{2.3cm}p{5.9cm}p{4.6cm} :font \scriptsize
| *Test*          | *What it checks*                                 | *For our shop*                        |
|-----------------+--------------------------------------------------+---------------------------------------|
| Unit            | One function, isolated, milliseconds             | ~average([10, 20]) == 15~             |
| Integration     | Several parts together (code + DB, + file, + API) | cart saved to and read from the DB    |
| Contract        | Two services agree on the API format             | the front-end and the cart API        |
| End-to-end (UI) | A robot uses the real app, like a user           | add to cart, pay, see the receipt     |
| Acceptance      | The feature does what the *client* asked         | "Given 2 items, when..., then..."     |
| Regression      | An old bug never comes back                      | the 150% discount test of lab 2       |
| Smoke           | Is it alive at all? A few seconds, after deploy  | the home page answers 200             |

#+BEAMER: \vfill
#+begin_keyblock
Regression is not a level but a *purpose*: any test kept after a bug is a regression test.
#+end_keyblock

** Non-functional tests: does it do it well?

#+ATTR_LATEX: :booktabs t :align p{3.2cm}p{6.2cm}p{3.6cm} :font \scriptsize
| *Test*                | *Question*                                            | *Tools*                 |
|-----------------------+-------------------------------------------------------+-------------------------|
| Performance / load    | Response time with 1\,000 users at once?              | =locust=, k6, JMeter    |
| Stress                | Where does it break, and does it recover?             | same tools, more load   |

| Compatibility         | Every OS, browser, Python version?                    | matrix builds           |

| Exploratory (manual)  | What did nobody think of?                             | a curious human         |

#+begin_keyblock
A correct app that answers in 30 seconds, or leaks data, is still a broken app.
#+end_keyblock

** Can we trust the tests?

*** Left
:PROPERTIES:
:BEAMER_col: 0.5
:END:

*Flaky tests*
- Sometimes green, sometimes red, same code
- Causes: time, randomness, order between tests, network, shared state
- The team learns to "just re-run": CI loses its meaning
- Fix it or quarantine it *now*

*** Right
:PROPERTIES:
:BEAMER_col: 0.5
:END:

*Testing the tests*
- *Mutation testing*: the tool changes the code (=<= \rightarrow =<==, =+= \rightarrow =-=); a good suite turns red. Tool: =mutmut=
- *Property-based testing*: the tool generates hundreds of inputs ("for any list, =total >= 0="). Tool: =hypothesis=

*** Conclusion
:PROPERTIES:
:BEAMER_env: ignoreheading
:END:

#+BEAMER: \vfill
#+begin_warnblock
A test that fails at random is worse than no test: people stop believing red.
#+end_warnblock

** When does each check run?

** Secrets

- Pipelines need passwords: a deployment key, an API token (next sessions)
- *Never* in the YAML: the workflow file is in the repository, and the repository may be public
- Settings > Secrets and variables > Actions, then in the workflow:

#+BEAMER: \small
#+begin_example
      - run: ./deploy.sh
        env:
          API_TOKEN: ${{ secrets.API_TOKEN }}
#+end_example
#+BEAMER: \normalsize

- GitHub hides the value in the logs (=***=); PRs from forks do not get the secrets

#+begin_warnblock
Lecture 2 again: a secret pushed once stays in the history forever. The same holds for a secret printed in a public CI log.
#+end_warnblock

*** Do

- Fix it in minutes, or *revert* the guilty commit (lecture 2)

- Merge more changes on top of a red =main=

** Key takeaways

1. CI = a *practice* (integrate daily) + a *machine* (verify each integration)
2. CI starts from a *fresh machine* and only what is committed: no more "works on my machine"
3. GitHub Actions: a *workflow* file in the repository; events, jobs, steps, runners
4. Results appear *in the PR*; a *required check* blocks the merge on red
5. Machine first (lint, tests), human second (design, behaviour)
6. Keep it *fast*; a red =main= is the top priority: fix or revert
7. Many kinds of checks, each answering a *different question*: cheap ones on every change, expensive ones less often
